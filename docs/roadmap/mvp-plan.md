# MVP 实施计划

本计划按依赖顺序实施，不承诺未经估算的日期。每个里程碑只有满足退出条件后才进入下一阶段，避免用页面演示替代运行闭环。

## M0：基线评审

交付物：

- 产品范围与非目标；
- 系统架构和数据模型；
- 用例 JSON Schema；
- 适配器协议和清单 Schema；
- API 基线；
- 八个页面线框；
- 32 个星火 Agent 案例目录；
- MVP 验收清单。

退出条件：业务、测试和研发共同确认核心对象、用例语义、失败分类、安全边界和第一版范围。

## M1：平台工程骨架

计划仓库结构：

```text
apps/
  web/
  api/
  scheduler/
  worker/
packages/
  contracts/
  case-schema/
  adapter-sdk/
  execution-engine/
  executors/
  reporting/
adapters/
  spark-x-agent/
schemas/
infra/
  compose/
docs/
```

交付物：TypeScript工作区、代码质量工具、GitHub Actions、Docker Compose、PostgreSQL迁移、Redis队列、MinIO、健康检查和开发环境说明。

退出条件：全新环境可以一条命令启动，健康检查覆盖所有依赖，平台自身测试可在GitHub Runner运行且不访问内网测试环境。

## M2：测试资产控制面

交付物：

- 系统、模块、环境和目标白名单；
- 密钥引用与输出脱敏；
- 用例、公共步骤、数据集和不可变版本；
- Schema驱动步骤编辑器；
- 发布静态校验、比较、回滚、导入导出；
- 套件管理和用例模板。

退出条件：用户能完全通过页面创建一个HTTP业务用例，发布、加入套件、导出、回滚并恢复历史版本；明文密钥无法进入用例或日志。

## M3：执行与证据闭环

交付物：

- Worker租约、心跳、优先级和并发槽；
- 隔离执行容器；
- Chromium、HTTP、MCP、等待、变量、JSON和只读数据库执行器；
- 条件、受限循环、Fixture与finally；
- 资源锁、副作用登记和补偿清理；
- 截图、日志、Trace和结构化附件；
- 运行中心、详情页和SSE进度；
- 八类结果与三类门禁结论。

退出条件：故意注入产品、脚本、环境、基础设施和Worker中断故障时，平台分类正确；取消和超时都执行清理；首次失败不会被重试覆盖。

## M4：星火 Agent 适配器与案例

交付物：

- 星火 Agent 环境 `192.168.110.136` 接入；
- 登录会话、聊天、工具、知识库、Skill、MCP、自动任务和最近会话能力；
- 可获得时接入结构化工具调用和命中文档证据；
- 固定 Provider 的确定性测试通道；
- 真实模型多次运行及成功率聚合；
- 32 个首批案例和对应套件。

退出条件：B2C 订单案例能对“订单文件命中”和“科目表误命中”作稳定相反判定；七个模块均有P0主路径通过；CRUD资源清理无残留。

## M5：计划、门禁和报告

交付物：

- 显式时区的定时计划；
- API/Webhook触发和幂等；
- 发布平台回调及签名；
- 冒烟阻断和全量回归可配置门禁；
- Allure或等价的人类可读报告；
- 通用Webhook通知；
- 附件过期和锁定策略。

退出条件：发布平台可以触发冒烟，稳定获得`passed|blocked|inconclusive`和报告地址；重复Webhook不会生成重复运行。

## M6：可靠性、备份与验收

交付物：

- 平台自身全量测试；
- 容量和并发压测；
- 数据库备份、MinIO策略和恢复演练；
- 40核/32GB测试机的资源上限调优；
- 独立Docker Compose部署与升级/回滚说明；
- 运维手册和已知限制。

退出条件：完成 [`../quality/acceptance.md`](../quality/acceptance.md) 的全部强制项，并由独立人员按文档在干净环境完成一次部署、运行、故障恢复和数据恢复。

## 开发纪律

1. 每个里程碑以可验证纵向切片为主，不同时铺开所有页面。
2. Schema、状态机和API先于界面实现，界面不维护第二套事实模型。
3. 新执行器和适配器必须先有契约测试。
4. 真实模型测试不替代确定性契约测试。
5. 不提前实现第一版非目标；新增范围先更新基线并评审。
